# 实施顺序与验收

当前仅完成设计文档，下面的实验与实现均未执行。

## 阶段一：先验证两个主要不确定性

### 来源验证

- 选取官方发布页、RSS、GitHub Releases、社区 API 等共 5 个来源，记录入口及解析效果。
- 单独验证 2～3 个公众号的采集与登录维护，不阻塞其他来源。
- 如需凭据，由部署配置提供；不把账号状态假设为已经具备。
- 在实际 QQ 环境验证主动消息权限、配额、消息长度、结果查询与回执能力。

### 去重评测

准备至少 100 条报道，人工标注其事件归属与事实增量，涵盖：中英同事件、转载改标题、同产品不同版本、旧闻重发、价格/下载后续、辟谣、同 URL 更新、多事件文章。

同时评估重复识别准确率、漏合并率、错误合并率和重要进展漏报率。向量阈值、候选数量和模型提示根据样本调整；保留独立测试集，避免只对示例有效。不将“文本相似度高”当成测试通过标准。

## 阶段二：实现不对外发送的完整链路

采集 → 提取事实 → 召回历史 → 事件关系判定 → 评分 → 快讯/日报/周报草稿。

输出每条候选的来源、事件 ID、增量、入选/未入选理由及模型成本。验证进程重启可恢复、历史回填不触发快讯、时间未知不冒充最新消息。

## 阶段三：优先实现订阅推送

实现订阅配置、持久化待投递表、Webhook worker、下游 inbox 去重、接收确认、执行回执、状态查询及反馈。QQ Bot 独立部署。博客增加受限发布入口及外部 ID 幂等性，遵守博客仓库的开发约定。邮件适配器通过邮件 API 或 SMTP 发送，区分服务商接收、投递与退信。

验证下列故障：重复订阅命中、重复调度、两个 worker 同时处理同一事件、配额竞争、接收确认丢失、发送成功后回执丢失、租约过期、消费者重启、平台限流、文章创建成功但请求超时。确认重试只影响失败渠道，已接收不被误判为已发布，邮箱接受请求不被误判为进入收件箱。

## 阶段四：增加拉取与离线恢复

在相同数据结构、幂等键与状态机上实现领取、续租、接收确认、恢复核对；支持 `pull` 和 `push_with_pull_recovery`。原有推送订阅无需重建内容或投递记录。

验收场景：

- 推送和拉取同时领取，只产生一个有效执行授权。
- 下游离线期间生成任务，重启后只补齐仍有效且尚未执行的任务。
- 已推送成功但回执丢失时，先核对，不因拉取而重复发布。
- 已接收任务租约过期，旧执行者仍在运行或回执迟到时，不盲目重派。
- 过期快讯、跨日配额、积压恢复限速、纯拉取下游、多订阅相同目标均遵循统一规则。
- 拉取只能访问授权目标；历史只读查询不触发投递。

## 阶段五：试运行与反馈

使用小范围目标渠道观察重复推送、重要新闻漏报、端到端延迟、来源健康、日报质量及调用成本。根据用户反馈调整主题权重与评分，保留调整历史。

## 实现前的配置事项

- 发布时区、日报时间、周报星期与时间。
- 实际 QQ 目标与主动发送能力。
- 模型和 embedding 提供商、搜索服务商、日预算。
- 首批公众号名称及可用采集条件。
- 博客受限凭据与发布入口方案。
- 各渠道订阅类型、主题、目标、推送地址或拉取模式。
- 快讯有效期、报告补投范围、离线恢复速率与邮件服务配置。

这些事项不阻碍本地数据结构与无投递链路的开发，但依赖它们的上线行为必须在配置明确后启用。
